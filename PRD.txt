Product Requirements Document: Azure Spot VM Placement Score Analysis Tool
Overview
Azure Spot Virtual Machines offer significant cost savings by using surplus capacity, but their availability is unpredictable and they can be evicted at any time[1][2]. Microsoft Azure introduced the Spot Placement Score to help predict the likelihood of successfully deploying Spot VMs in a given region or zone for specific VM sizes[3]. The Spot Placement Score is a qualitative indicator – High, Medium, or Low – which signifies how likely a Spot VM deployment will succeed under current capacity conditions[3]. A High score means the deployment is very likely to succeed, whereas Low indicates a low chance of success[3]. However, this score is only valid at the moment of query and can change throughout the day[4]. It also doesn’t guarantee zero evictions or long-term availability stability[5].
In addition to real-time placement scores, Azure provides historical Spot VM metrics via the Azure Resource Graph. These include up to 90 days of price history and 28 days of eviction rate data for each VM SKU in each region[6]. By analyzing historical spot price trends and eviction rates, users can identify which VM sizes and regions tend to be cheaper and less likely to be evicted over time[7]. For example, the eviction rate indicates the chance a VM will be evicted within the next hour based on recent history (e.g. a 10% eviction rate means a 10% chance of eviction in the next hour, based on the last week of data)[8].
Problem Statement: The user needs to determine which Spot VM SKU (size) and region is optimal for their workloads, by considering: (1) current availability (placement score), (2) historical stability (eviction rates), (3) cost (spot pricing), and potentially (4) capacity (how many instances can be obtained). Doing this manually for multiple SKUs and regions and tracking how conditions fluctuate over the day is complex. The goal is to create a Python-based tool that automates this analysis, helping to identify the best region+SKU combinations for Spot VMs given the criteria above.
Objectives and Goals
Combine Real-Time and Historical Insights: Leverage Azure’s Spot Placement Score API to get immediate availability likelihood for specified VM sizes and regions, and Azure Resource Graph to fetch historical spot price and eviction rate data[3][6].
Compare Multiple SKUs and Regions: Allow the user to input a list of candidate VM SKUs and target regions. The tool will evaluate all combinations (up to Azure’s limits of 5 VM sizes and 8 regions per request for placement score[9]) and identify which combinations offer the best trade-off: high success probability, low eviction rate, and low price.
Inform Deployment Decisions: Produce a clear comparative report (initially as console/ASCII tables) that answers “Which of the given SKUs in which region should I use for my Spot VM workloads?” based on the current score and historical trends. This will help optimize for fewer evictions, lower cost, and successful deployments.
Monitor Fluctuations: Because spot availability and prices can change by time of day[1][6], the tool should support repeated execution (or scheduling) to capture how placement scores and capacity indicators change over the course of the day. This can reveal daily patterns and further guide scheduling of workload or choice of region.
Key Features and Requirements
Functional Requirements
1. Python Implementation: The solution will be implemented in Python (e.g. using Azure SDK or REST calls) to facilitate automation and scripting flexibility. Python was chosen for its rich ecosystem and ease of integrating with Azure APIs.
2. Input Configuration: Users can specify:
A set of VM sizes (SKUs) of interest (e.g. Standard_D2s_v4, Standard_D4s_v4, etc.).
A set of Azure regions (e.g. eastus, westus, centralus, etc.) where they are considering running the Spot VMs.
The desired number of instances (Spot VMs count) for the deployment scenario. This “desired count” will be used in the placement score query, since the score is sensitive to how many VMs you want to launch (a larger batch might have a lower score)[10].
(Optional) The OS type (Linux/Windows) for price and eviction queries, since spot price history may differ by OS. By default, Linux will be assumed if not specified.
3. Azure Spot Placement Score Query: The tool will call the Azure Spot Placement Score API to evaluate the likelihood of a successful deployment for the given combinations of SKUs and regions. Azure allows querying up to 5 VM sizes and 8 regions at once in a single API call[9]. If the input list exceeds these limits, the tool will batch the requests appropriately. Key details:
API Endpoint: POST /subscriptions/{sub}/providers/Microsoft.Compute/locations/{region}/placementScores/spot/generate?api-version=2025-06-05[11]. (One of the regions is used in the endpoint, but the payload contains all desired regions.)
Payload: The request includes the list of desiredLocations (regions), desiredSizes (SKUs), desiredCount (integer), and availabilityZones flag[12]. For regional scope (no specific AZ), availabilityZones can be false/null.
Authentication & RBAC: The tool will use Azure credentials (such as an Azure AD service principal or user token). The calling principal must have the “Compute Recommendations Role” assigned on the subscription to use this API[11].
Output Processing: The API returns placement scores per combination of (region, [zone], SKU). Each combination comes with a placementScore value (High/Medium/Low) and an indicator if quota is available for that SKU in that region[13][14]. For example, a response might show that for Standard_D4_v2 in westus, the score is Low whereas in eastus it’s High[15]. The tool will parse this response and capture the score (High/Med/Low) for each SKU-region pair, and note if any are not feasible due to quota.
4. Azure Resource Graph Queries (Historical Data): The tool will query Azure Resource Graph to retrieve historical spot information from the SpotResources table[16]. Two types of data will be fetched for the specified SKUs and regions:
a. Spot Price (USD) History: Using a query against microsoft.compute/skuspotpricehistory records, filtered by the given SKU names and regions. From the results, the latest spot price will be extracted for each SKU-region (this gives the current or most recent hourly price)[17]. The query will ensure we match the OS type (e.g., Linux) for accurate pricing[17]. Example: A sample query projects latestSpotPriceUSD = todouble(properties.spotPrices[0].priceUSD) for each SKU and location[17] (the first element of the spotPrices array is the latest price). The tool will use a similar query and parse the output to get a numeric price in USD for each combination.
b. Spot Eviction Rate: Using a query against microsoft.compute/skuspotevictionrate records, filtered by SKU and region. The query will retrieve the properties.evictionRate for each SKU-region[18]. This eviction rate (a percentage) represents the recent probability of eviction for that VM size in that region (based on trailing 28 days of data, per Azure documentation)[6]. The tool will collect this percentage (e.g., "5%" or "10%") for each combination.
Both queries can be executed via the Azure Resource Graph API or Azure CLI. The tool might use the Azure SDK (if available for Resource Graph) or call the REST API directly. Since these queries are read-only and scoped to publicly available Spot data, they should not require special permissions beyond read access to Resource Graph (which generally every Azure user has by default).
5. Data Synthesis: The tool will combine the real-time placement score data and the historical metrics into a unified view. For each VM SKU and region pair, we will have:
Placement Score: High/Medium/Low (qualitative likelihood of getting the Spot VM now)[3].
Spot Price: Latest price in USD/hour (to compare cost – a lower price is better).
Eviction Rate: Recent eviction rate in % (lower means the VM is historically less likely to be evicted unexpectedly).
Quota Flag (if available): Whether the user’s subscription has enough quota for the requested number of VMs of that SKU in that region. This is returned by the placement score API (“Is quota available?” boolean)[13]. If quota is False for a combination, the tool may flag it (since even if capacity is available, the deployment would fail due to quota limits).
6. Output Format – ASCII Tables: Initially, the output will be printed as text-based tables to the console (suitable for terminals or logs). The tables will be organized for clarity:
One combined table listing each (Region, VM SKU) combination as a row, with columns for Placement Score, Latest Price, Eviction Rate, and Quota Available. For example:

If the number of combinations is very large (e.g. dozens of SKUs across many regions), the tool might group output by SKU or by region for readability. However, initial implementation will focus on a reasonable number of combinations (since the placement score API itself limits input size per call).
7. Ranking & Recommendations: The primary role of the tool is to present data objectively, but it can also provide simple insights, such as:
Highlighting the “best” combination(s) based on certain criteria. For example, it might sort the table by Placement Score (High first), then by lowest Eviction Rate, then by lowest Price. Or it could flag any combination that meets all desired thresholds (e.g. High score and eviction < 5% and price < $X).
The logic for ranking can be adjusted by the user, but an initial approach might be: prefer High over Medium over Low; among those with the same score, prefer lower eviction; if eviction is similar, prefer lower price. The PRD scope is primarily to display data, so any automated recommendation will be kept simple.
8. Visualization (Low Priority / Future Feature): As an enhancement, the tool may offer visualization of the data and trends. This could include:
Plotting historical price trends for each SKU in each region (e.g. a line chart for the last 90 days of prices if needed).
Bar charts comparing eviction rates across regions for a given SKU, or vice versa.
Time-of-day placement score changes (if the tool is run periodically, it could log scores and later graph how a certain combination’s score fluctuates over 24 hours).
These features are marked as low priority – the initial focus is generating the ASCII tables output. Visualization could be enabled via an optional flag or as a separate module (perhaps leveraging libraries like Matplotlib or Plotly in Python).
9. Execution Frequency: The tool is intended to be run on-demand, but the user has an interest in understanding time-based fluctuations. Therefore:
It should be lightweight enough to run multiple times a day (e.g., morning, afternoon, evening) without excessive cost or hitting rate limits. The placement score data is ephemeral and can be polled periodically[4], and Azure recommends caching identical requests for at least 15 minutes to avoid spamming the service[19]. We will adhere to this by caching results for a given (SKU set, region set, count) combination if the tool is invoked again within a short interval.
A stretch goal is to allow scheduling. For instance, a user could run the script via cron or a scheduler to automatically collect data at set intervals. The script could append timestamped results to a log or database for later analysis of trends. This PRD scope doesn’t mandate building a full scheduling system (that can be handled externally), but the script should be designed to support repeated executions smoothly (idempotent caching, logging, etc.).
Non-Functional Requirements and Considerations
Azure Access: The user must have an Azure subscription and appropriate access. Particularly, calling the Spot Placement Score API requires the Compute Recommendations RBAC role on the subscription[11]. The tool should provide clear instructions or checks for this (e.g., if the API returns an authorization error, inform the user to assign the role). Azure Resource Graph queries require the user to have at least read access to the subscription’s resource data (in practice, most users do, as ARG can query public pricing/eviction info without special roles).
Performance: The API calls and graph queries are expected to be relatively fast. The placement score API internally gathers data but should return quickly for a handful of regions/VMs. The Resource Graph is optimized for queries and can handle large datasets. The tool should keep the data volume manageable by filtering to only needed SKUs/regions in queries[7]. If a very large query is needed, the tool might break it into smaller queries per SKU group to avoid timeouts.
Error Handling: The tool should handle common errors gracefully:
“Data Not Found or Stale” responses from the placement score API (meaning the underlying data isn’t available or fresh)[20][21]. In this case, the tool might retry after a backoff or inform the user that data is currently unavailable for those inputs.
HTTP errors or timeouts from any API calls. The script should catch exceptions and output a meaningful error message (not a raw stack trace).
Rate limiting: The placement score API counts against the subscription’s GET quotas[22], and returns HTTP 429 if too many requests[23]. The tool will mitigate this by caching and by not exceeding recommended call rates (no more than one identical call per 15 minutes)[19]. If a 429 is encountered, the tool will pause and retry after a delay.
No Cost Overhead: Using the Spot Placement Score feature is free of charge[24]. Azure Resource Graph queries are also free to execute. The only cost related factor is if the user decides to launch actual VMs based on the recommendations, but that is outside the scope of this tool. The tool itself should not trigger any Azure resource creation or incur costs.
Security: The tool will require Azure credentials (likely provided via environment variables or Azure CLI authentication context). These should be handled securely. No sensitive data is stored by the tool except perhaps caching the query results in memory or local file. If logs are kept for multiple runs, they should not contain secrets.
Maintainability: The script should be written in a clear, modular way (e.g., separate functions for calling placement score API vs querying resource graph vs formatting output). This will make it easier to update if Azure changes their API (for example, if a new API version or new metrics become available). The PRD does not require a full design of code modules, but the implementation should follow best practices for readability.
Approach and Implementation Details
To achieve the above requirements, the development will be broken down into phases:
Phase 1: Data Retrieval Module
Placement Score Fetcher: Implement a Python function to call the Spot Placement Score API. This can be done via the Azure REST API (using requests or the Azure Python SDK if it supports this preview API). The function will accept the parameters (subscription, regions list, sizes list, count, zones flag) and return the structured results (list of {region, zone, sku, score, quotaFlag}).
We will refer to Azure’s documentation for constructing the request properly. For example, we know the JSON payload structure and the need to include the API version 2025-06-05 and proper auth header[11].
If the Azure CLI is available in the environment, an alternative is to use az compute-recommender spot-placement-score command (which is GA and wraps the API)[25]. However, using the REST call or SDK directly is more straightforward in code.
Implement caching: use an in-memory cache (or simple file cache) with a key like (regions, sizes, count, zones) and timestamp. If the same query is made again within 15 minutes, reuse the previous result[19] to avoid redundant API calls. This cache could be reset if the script is long-running or could be simply ephemeral per run if running via short invocations.
Resource Graph Fetcher: Implement functions to query spot price and eviction data. Potential approaches:
Use Azure CLI internally (e.g., call az graph query -q "<query>" and parse JSON output). This requires Azure CLI to be installed and logged in.
Use the Azure Resource Graph REST API directly: POST to https://management.azure.com/providers/Microsoft.ResourceGraph/resources?api-version=2021-03-01 with a JSON body containing the query and subscriptions. This returns the query results in JSON. This approach needs an authentication token as well.
Use an Azure SDK like azure-mgmt-resourcegraph (if available), which can execute queries directly in Python.
For simplicity, initial implementation might use the CLI if we assume the environment has az available (since the user likely will run this in an Azure context), but the PRD leans towards using REST calls for a self-contained approach.
Two queries will be constructed (as noted earlier) using the input lists:
Price Query: Filter SpotResources by type == "microsoft.compute/skuspotpricehistory/ostype/location", by the given sku.name list and location list, and properties.osType if specified (Linux/Windows). Then select the relevant fields including the latest price[17].
Eviction Query: Filter SpotResources by type == "microsoft.compute/skuspotevictionrate/location", and by SKU and location, then select the evictionRate[26].
These queries will return datasets that the function can parse (probably as lists of records). We will map each result to a key (sku+region) for easy lookup. For example, get a dictionary of {(sku, region): price} from the first query, and {(sku, region): evictionRate} from the second.
Phase 2: Data Integration & Logic
With both sources of data retrieved, we merge them. We will iterate over each combination of interest (each SKU-region pair we queried) and gather: placement score, price, eviction, quota. There should be a match for each if data exists. In rare cases where one data source lacks a combination (e.g., the placement score API might omit a SKU if it’s not available at all in a region or data was stale), the tool should handle it (maybe mark as "N/A" or retry if appropriate). Azure’s documentation indicates “Restricted SKU” or “Data Not Found” might be returned in such cases[21]. The tool can surface that by marking that combination accordingly (e.g., score = "N/A" if data not found).
Calculation of Derived Insights: Beyond raw data, if needed, compute helpful info. For instance, if price and eviction rate are both collected, one could compute a simple “stability score” or cost-risk metric, but this might overcomplicate. The PRD does not require a new metric, but it’s something to consider in analysis (not necessarily implemented).
Selecting Best SKU/Region: The final step in logic could be to identify optimal choices. The definition of “best” can depend on user priorities (cost vs reliability). However, as a guideline, the tool can implement a default strategy: filter to only High placement score entries first, then among those pick the lowest eviction rate (and maybe secondarily lowest price). If no High scores, consider Medium, etc. The result could be output as a note like: “Recommended: Use Standard_D2s_v4 in eastus, which has High placement likelihood, low 5% eviction rate, and one of the cheapest prices.”
Phase 3: Output Generation
Format the consolidated data into ASCII tables as described. Python libraries like tabulate could help, or it can be manually formatted. Ensuring columns align and data is sorted in a logical order (e.g., group by region or by SKU) improves readability.
Include any highlights or color-coding in the console (optional). For instance, using ANSI colors to highlight “High” in green, “Low” in red, etc., if the user runs this in a true console. But for broad compatibility (and since the output might be copied elsewhere), simple text labels are sufficient.
If multiple tables are needed (for example, separate tables per region), ensure consistent formatting and labeling. However, a single unified table is likely more convenient for comparison across regions and SKUs.
At the beginning of the output, print a brief summary or key findings (if implementing the recommendation logic). This could be a short list of top candidates or observations (e.g., "All SKUs in westus have Low placement score currently – consider eastus or southcentralus instead").
Phase 4: Visualization (optional/future)
Implement a function to produce charts if the feature flag is enabled. For example:
Use Matplotlib to create a bar chart of eviction rates by region for each SKU (or vice versa).
Plot line graphs of spot price history (retrieved via an extended Resource Graph query for 90-day history) for the top candidate SKUs.
If multiple time-snapshots of placement scores are recorded (from scheduled runs), visualize how a score changes over time of day. This requires storing past runs’ data, which might be beyond initial scope.
The visualization results can be saved as images or possibly displayed (if in an interactive environment). Since this is a low priority, it might be implemented in a later iteration or left as a manual step (the user could feed the output data into their own visualization tool).
Deliverables
Python Script (Tool): A standalone Python program (or possibly a Jupyter Notebook for easier iteration) that fulfills the above functionality. It will be delivered with instructions on required Azure setup (Azure CLI login or service principal credentials, assigning RBAC role, etc.). The script will be well-documented internally for maintenance.
Sample Configuration and Output: The documentation will include examples of how to run the tool, with sample input parameters and an example output table. For instance, demonstrating the tool with two VM sizes across two regions (similar to the scenario examples in Azure docs) and showing the resulting table. This helps the user verify the tool’s behavior and interpret the results.
README/Guide: A markdown or PDF document explaining how the tool works, how to configure and run it, and interpreting the results. It will also mention the data sources and their meanings (recapping that placement scores are moment-in-time and may differ later[4], and eviction rates are historical averages[6], etc.).
Constraints and Assumptions
We assume the user has access to the Azure subscription and required permissions. Without the Compute Recommendations Role, the placement score API cannot be used – that is a hard requirement from Azure[11]. If this role cannot be granted, the tool’s placement score part won’t function. In that case, the tool could still rely on historical data alone, but that is a degraded mode. We will note this in documentation.
Azure’s SpotResources (price and eviction data) are available for all public regions and most common VM SKUs. If a very new VM size or a niche region has no data, the queries might return empty for those. The tool should handle missing data by informing the user that historical info is not available for certain combinations (they might be too new or not yet used in Spot).
The accuracy of recommendations is limited by the Azure data. A High placement score is a positive sign but not a guarantee[4] – spot VMs can still fail to allocate if another spike in demand occurs, and they can be evicted even if historically eviction rate was low[4][5]. The tool will include a disclaimer in the output or documentation that it provides best-effort guidance, not certainty.
The number of Spot VMs available ("number of nodes available") is not directly exposed by Azure. We infer capacity trends indirectly. If needed, the user can experiment with the desiredCount parameter – for example, query placement score with 10, 50, 100 VMs to see at what point the score drops. This could indicate how many might be provisioned with high confidence. However, automating this probing is not in the initial scope (to avoid too many API calls). We assume the user will specify a realistic desired count for their needs, and the score corresponds to that count’s likelihood.
Pricing data is in USD and hourly. If the user cares about different currency or a longer-term cost estimation, they might need to convert or extrapolate outside this tool. We stick to the raw spot price as given by Azure’s retail rates (which are in USD)[17].
Future Enhancements
Dynamic SKU/Region Discovery: In the future, the tool could auto-suggest other SKUs or regions not initially provided by the user that might be better. For example, if the user provided sizes in the D-series, the tool might check similar sizes or next-gen versions to see if they have better prices or availability. This would utilize Azure’s broad data (the SpotResources table could be queried without SKU filter to find any SKU under a price or eviction threshold in a region). This is beyond the current scope, which focuses only on user-specified options.
Integration with Deployment Pipelines: The tool could be integrated into an automated pipeline to actually deploy Spot VMs after recommending a SKU/region. For instance, it could feed into an ARM template or Terraform as input variables. This would make it a part of an intelligent provisioning system. The current PRD focuses on advisory output rather than taking action.
User Interface: A possible GUI or web dashboard might be built on top of this logic for easier use (especially if visualization is added). A web app could periodically poll data and display live dashboards of spot capacity scores. The current approach is a script/CLI for simplicity.
Extended Metrics: If Azure exposes more relevant data (like actual available capacity numbers or real-time eviction probability), the tool can incorporate those. Also, using the Azure Retail Prices API for more detailed price history or regional price differences beyond 90 days can complement the data[27].
Multi-Subscription or Scale Set Aware Analysis: In cases where the user has multiple subscriptions or wants to utilize VM Scale Sets with Spot instances, the tool could be extended to ensure those scenarios are covered (e.g., checking single vs. multi-zone placement behavior, and noting that other constraints like SinglePlacementGroup are not considered by the score[28]).
Conclusion
This PRD outlines a comprehensive Spot VM Analysis Tool that will help users make informed decisions about where to run their interruptible workloads in Azure. By combining the Azure Spot Placement Score’s real-time evaluation of capacity (High/Med/Low success likelihood for a given deployment) with Azure Resource Graph’s historical insights (price trends and eviction rates over time), the tool provides a balanced view of both current and future risk/cost.
The output – easily readable tables with key metrics – will enable quick comparison across VM SKUs and regions of interest. Users can identify, for example, that “SKU X in Region A has a High placement score and only 2% eviction rate, making it a better choice than SKU Y in Region B which is Medium and 15% eviction rate.” This data-driven approach removes much of the guesswork from using Spot VMs[29] and can significantly improve the success rate and cost-efficiency of Spot VM deployments[29].
By iterating on this tool and possibly adding visualizations and scheduling, the user will also gain visibility into how spot capacity and prices fluctuate (e.g., discovering a region that is usually fine at night but risky at noon). In summary, the delivered script will serve as a valuable component in optimizing Azure Spot VM usage, aligning with the goal of running workloads on the most cost-effective and reliable spot infrastructure available[7].
